# case-specification

把每条验收标准展开成用例规格时用它。

**产出的是规格,不是可执行测试。** 你没有 Bash、也读不到业务仓——你写不出"跑过一遍、
红在断言上"的测试,那是出题人的活。你定的是**这次要验什么**,它定的是**怎么编码**。

这条边界是有意的:验收用例是稳定的契约(需求不变它就不变),单元用例是易变的脚手架
(重构即重写)。把易变物放进环节间契约会让流水线频繁空转。

## 一条标准一份规格

按标准的 id 编址,一条标准一份文件。**先把标准逐条抄下来再逐条展开**——凭印象写完再回头
对,漏掉的那条永远是最不显眼、也最容易在实现里被绕过的那条。

## 每条用例的形状

- **Given**:一个**可构造**的系统状态。说得出怎么把系统弄成这样,才叫可构造;
  「系统处于高负载」不是状态,是形容词。
- **When**:**单一**触发动作。两个动作就是两条用例。
- **Then**:**可断言**的可观测结果。说得出期望的具体值。

**三者任何一处出现"合理地""正确地""及时地""正常"之类的词,这条就不合格。** 它们看起来
像标准,但没有任何一次执行能判定它们真假——而下游会把它当成已经定好的事往下走。

## 技术逐条过一遍(不是可选技巧)

- **等价类划分**:每个输入域的每个等价类至少一例;
- **边界值**:每个边界取**两侧**(上限、上限 +1);
- **状态迁移**:合法迁移逐条覆盖,非法迁移至少抽查;
- **决策表**:多条件组合时先列表再选行,不要凭感觉挑几种组合;
- **错误猜测与否定测试**:空、零、负数、重复、并发、依赖抛异常。

## 两条硬规则

1. **每条标准至少一个正例和一个反例。** 只有 happy path 的用例集等于没写异常语义——
   而它会让"没被验过"看起来像"验过了"。
2. **必须有不变量用例。** 需求没提到、但本次变更**不许破坏**的现有行为,从行为基线
   (现有回归用例、相关模块的接口契约)里选取,作为回归锚。没有基线就没法区分
   「新行为」与「不能破坏的旧行为」。

## 反例

- ❌ 「Given 系统正常运行,When 用户下单,Then 下单成功」
  ← Given 不可构造,Then 不可断言。三处有两处是形容词
- ❌ 只写「下单 3 件库存 10 → 成功」 ← 缺反例。库存不足那条路没人验
- ❌ 「Given 库存 10,When 下单 3 件并取消订单,Then 库存回到 10」 ← When 有两个动作
- ✅ 「[a1/正例/等价类:库存充足] Given SKU-1 库存 10;When 下单 3 件;
  Then 下单成功,SKU-1 剩余 7」
- ✅ 「[a1/反例/边界:恰好不足] Given SKU-1 库存 2;When 下单 3 件;
  Then 下单失败,SKU-1 仍为 2,且无预占记录」
- ✅ 「[a1/不变量] Given 已有订单 ord-9 预占 SKU-2 共 5 件;When 执行上述任一用例;
  Then ord-9 的预占不变(基线用例 `test_existing_reservation_survives`)」

## 自检

- [ ] 每条验收标准都有一份对应的规格
- [ ] 每条标准正例与反例各至少一条
- [ ] Given 都可构造、When 都是单一动作、Then 都可断言
- [ ] 没有一处出现"合理地""正确地""及时地""正常"这类判不了的词
- [ ] 五类技术逐条过了一遍,不适用的知道为什么不适用
- [ ] 有不变量用例,且它引用的基线用例真的存在
