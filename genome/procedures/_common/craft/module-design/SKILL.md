# module-design

写实现时用它。**判据只有一条:这次改动让模块的公开面变宽了多少,值不值。**

一个好模块是"很多功能藏在一个小接口后面"。它变坏很少是一次大事故,而是几十次"顺手多导出
一个函数"累积出来的——每一次都合理,每一次都没人拦,而评审很难单独指着其中任何一次说不。
这份手艺是那几十次里的每一次要问的那句话。

## 步骤

1. **动手前先说出这次要新增的公开面。** 哪些函数、类型、字段是别的模块能看见的。
   一个都不新增是最好的结果——**改动的理想形态是"接口没变,行为变了"**。
2. **每个新增的公开项问一句:调用方真的需要它吗?** 说不出具体的调用方与用途,就别公开。
   已经写好了也别公开:内部函数不加前缀导出、类型不放进包的对外命名空间。
3. **参数表体现的是调用方的需要,不是实现的方便。** 让调用方传三个只有实现才懂的开关,
   等于把实现细节漏了出去——那三个开关将来一个都改不动。
4. **错误也是接口。** 抛出去的异常类型、返回的错误码属于公开面。新增一种错误要问:
   调用方拿它做什么?没有分支要走的话,归到既有那类里。
5. **跟着周围的写法走。** 同一个仓里出现第二套做法的成本,通常高于第一套写法的任何缺点。

## 遇到"接口不够用"时

想做的事现有接口支持不了,有两种走法,**先分清是哪一种**:

- **这个模块本来就该会这件事** → 加一个方法,把复杂度留在里面;
- **这是调用方自己的事** → 别往模块里塞,在调用方组合既有接口完成。

分不清就写进 `questions[]`,附上你倾向的选项与理由。猜错的代价是一个将来谁都不敢改的接口。

## 反例

- ❌ 为了测试方便把内部函数导出 ← 测试要走公开面走(见 `tdd-loop`);导出之后它就是接口了
- ❌ 新增 `process(data, mode, legacy=False, strict=True)` ← 四个参数里三个是实现细节
- ❌ 「先加个通用的钩子,以后可能用得上」 ← 需求里没有的抽象,删掉;真需要时再加
- ❌ 一个 helper 只被一处调用却放进了模块的对外命名空间 ← 它是实现,不是接口
- ✅ 「本次公开面零新增:`reserve()` 的签名没变,库存不足的分支走既有的
  `InventoryShortage`;回滚逻辑留在模块内部」

## 自检

- [ ] 说得出这次新增了哪些公开项(理想是零)
- [ ] 每个新增项都指得出具体的调用方与用途
- [ ] 没有为了测试而放宽可见性
- [ ] 参数表里没有只有实现才懂的开关
- [ ] 新增的错误类型都有调用方要走的分支
