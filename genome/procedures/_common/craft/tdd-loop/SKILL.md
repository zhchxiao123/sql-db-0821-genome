# tdd-loop

实现一个需求或修一个缺陷时用它。**它讲的是循环怎么走**;一条用例本身怎么写好
(边界清单、断言什么不断言什么)是 `test-design` 那一份的事,这里不重复。

## 一次一片,不是先写完所有测试

拿到一份验收标准,最诱人的做法是把所有用例先写出来,再一口气实现。**别这么做。**

批量写出来的用例验的是**你想象中的行为**:那时你还没写实现,不知道哪些边界真的存在。
它们会长成"形状对、行为空"的样子——名字齐、结构齐,而任何一个真实的行为改动都碰不响
它们。而且你在还没理解问题之前就把测试结构定死了,后面每一次认知更新都要先去改测试。

正确的走法是**一次一片**:一条用例 → 刚好让它绿的实现 → 下一条。每一片都是一发曳光弹,
根据上一片学到的东西调整下一片的方向。

## 循环的四条规矩

1. **先红后绿。** 先写失败的用例,再写实现。反过来的话,你永远不知道那条用例是不是真的
   验到了东西——一条写在实现之后的用例,天生就是绿的。
2. **红要红在断言上**(怎么算红在断言上、一条用例本身怎么写好,见 `test-design`,
   这里不复述)。
3. **只写刚好够绿的实现。** 不提前实现下一条用例要的东西,不为想象中的将来留参数与钩子。
4. **重构不在循环里。** 循环只管红→绿。改结构是评审那一步的事——混在一起的话,一个提交里
   既改行为又改结构,评审分不清哪部分是真正的改动。

## 专职出题那一档下也仍然是一次一片

出题人与实现人分开时,你拿到的是**一批已经写好的红用例**。那张图看起来在鼓励你一口气
全绿——**不是**。写集分离换来的是"同一个头脑不会用测试抓自己的盲区",那是真收益;
但如果你据此一次性铺开实现,分工的成本付了,批量实现的坏处还在。

做法:把那批用例排个序(先窄后宽、先主路径后边界),一次让一条变绿,每条绿了再看下一条。
一条题出错了(它断言的不是验收标准说的事)就说出来——**你不能改它**,但可以在
`questions[]` 里说明"这道题我认为出错了,理由是……"。

## 反例

- ❌ 一次提交里 12 个新用例 + 完整实现 ← 分不清哪条用例真的验到了东西
- ❌ 先把 8 条用例全写完再动实现 ← 那 8 条验的是你**想象中**的行为:那时你还没写实现,
  不知道哪些边界真的存在
- ❌ 用例红在 `ImportError` 上就去写实现 ← 那不是红,那是还没开始
- ❌ 顺手把测试改成能过 ← 测试失败是信息,不是障碍。题出错了就说出来,不要改掉它
- ✅ 写一条断言"库存不足时抛 InventoryShortage 且预占记录数不变"的用例 → 跑 → 红在断言上
  → 写最小实现 → 绿 → 下一条

## 自检

- [ ] 每一片都是"一条用例 → 一次最小实现",没有批量铺开
- [ ] 每条用例都先跑过一遍,而且红在断言上
- [ ] 没有为下一条用例提前写实现
- [ ] 没有改动任何既有用例来让它通过
- [ ] 结构性的改动没有混进红→绿那几个提交里
