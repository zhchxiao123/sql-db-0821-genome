# vertical-slicing

产出拆分提案、要决定**怎么下刀**时用它。要不要拆是另一件事(判据是"单任务交付不可审或
不可行",而且不拆是默认);这份手艺只管既然要拆,刀往哪儿落。

## 每一片是一发曳光弹

一个子需求是一条**纵穿全部集成层的窄路径**:数据、接口、界面、测试都碰一点,做完之后
**有人能看到一个变化**。而不是横着切一层("先把 schema 改了""再把接口补上")。

为什么这条是硬要求,而不是审美偏好:子需求是**普通需求**——同一个队列排队、走完整状态机、
**各自成 PR**。一个横切出来的「先把 schema 改了」既不可单独验收(它没改变任何可观察行为),
也不该单独成 PR(审的人看不出它要干什么)。**机器拦不住这种拆法**:数量界限、无环、批内
引用,schema 那几条它全过。所以它只能靠这份手艺拦。

## 步骤

1. **每片先写一句"做完之后谁能看到什么变化"。** 写不出来的,它就不是一片,是一层。
2. **每片自带可判定的验收标准。** 它的 `text` 会被原样提交进需求队列,那时候没有人会回来
   帮它补——见 `acceptance-authoring`。
3. **先窄后宽。** 第一片走通最主干、最能暴露未知的那条路;后面的片在它证实的结构上加宽。
   把最不确定的留到最后,是把风险堆在了最贵的地方。
4. **依赖只写真实的交付依赖。** 下游要在上游**合入之后的代码**上继续,才算依赖。
   "先做 A 比较顺"不构成依赖——写上它只会让 A 白白挡住 B,而这种阻塞没人看得出是多余的。
5. **预重构单独成片,而且排第一。** "先让改动变容易,再做那个容易的改动"是合法的一片,
   条件是它自己不改变行为,而且说得出它让后面哪几片变容易。

## 反例

- ❌ 「① 改数据表 ② 补服务层 ③ 接前端 ④ 补测试」 ← 四层横切。①②④ 单独都不可验收,
  而且四个 PR 里有三个审的人看不出要干什么
- ❌ 「① 后端全部 ② 前端全部」 ← 还是横切,只是切成了两块大的
- ❌ 「② blocked_by [①],理由:先做 ① 顺手」 ← 不是交付依赖。② 会白等
- ❌ 一片的 `text` 只有一句"实现库存模块" ← 没有验收标准,它进队列之后没人能判它做完没有
- ✅ 「① 单 SKU 下单预占:一个 SKU、一次下单、成功与库存不足两条路径,端到端跑通
  (验收:下单 3 件库存 10 → 成功且余 7;下单 3 件库存 1 → 失败且余 1)」
- ✅ 「② 多 SKU 批量预占,blocked_by ①:要在 ① 合入后的预占接口上扩批量语义」

## 自检

- [ ] 每片都写得出"做完之后谁能看到什么变化"
- [ ] 每片的 `text` 自带可判定的验收标准
- [ ] 没有一片是"只改一层"
- [ ] 每条依赖都是真实的交付依赖,说得出下游要用上游合入后的什么
- [ ] 第一片走的是最主干、最能暴露未知的那条路
