# smell-baseline

评审规范轴时,**项目自己什么都没写下来**的那种情况用它。

规范轴的纪律是"判据不足就说判据不足"(见 `rule-compliance`),这条对——但它的代价是:
一个没写过规则文件的项目,评审基本产不出 major 以上的意见,于是那道闸形同虚设。
这份基线是那个空缺的填法:**一套不依赖项目文档也成立的坏味道清单**。

## 两条铁律,先于清单

1. **仓库写下的规范压过基线。** 规则文件或约定卡片明确认可某种写法时,基线上的对应条目
   **当场作废**,不许拿它提意见。基线是缺省值,不是标准。
2. **每一味都是判断题,不是硬违规。** 写成"疑似 X",给出它会让下一个人多付什么成本。
   把启发式写成断言,评审就变成了"评审员工的口味"——那是所有人都无法反驳也无法执行的事。

另外:**工具已经管的不要重复提**。格式化、import 顺序、行长由 linter 管,评审提它只是噪声。

## 十二味(逐条比对这次的 diff)

每条读作 *是什么 → 怎么改*:

- **名不副实** — 函数/变量/类型的名字说不清它做什么、装什么 → 改名;起不出诚实的名字,
  说明设计本身还没想清楚。
- **重复代码** — 同一形状的逻辑在这次改动的多个 hunk 或文件里出现 → 抽出来,两处都调它。
- **依恋情结** — 一个方法读别的对象的数据比读自己的还多 → 把方法搬到它依恋的那份数据上。
- **数据泥团** — 同几个字段总是一起出现在参数表里(一个类型想要诞生) → 打包成一个类型。
- **基本类型偏执** — 用字符串/整数顶替一个本该有自己类型的领域概念 → 给那个概念一个小类型。
- **重复的 switch** — 对同一个类型的 `switch`/`if` 级联在改动里出现多处 → 换成多态,
  或者一张两处共用的映射表。
- **霰弹式修改** — 一个逻辑变更逼你在很多文件里各改一点 → 把一起变的东西收到一个模块里。
- **发散式变化** — 同一个文件因为几件互不相干的原因被改 → 拆开,让每个模块只因一个理由变。
- **夸夸其谈的通用性** — 为需求里没有的场景加的抽象、参数或钩子 → 删掉,等真的需要再加。
- **过长的消息链** — `a.b().c().d()` 这种调用方不该依赖的导航 → 在第一个对象上开一个方法
  把这段路藏起来。
- **中间人** — 一个类或函数大部分工作只是转发 → 去掉它,直接调真正的目标。
- **被拒绝的遗赠** — 子类忽略或覆盖了继承来的大部分东西 → 别继承了,改用组合。

## 反例

- ❌ 「代码风格与最佳实践不符」 ← 哪一味?哪一行?精化那一轮改什么?
- ❌ 「这个函数超过 50 行,建议拆分」 ← 行数不是味道;说不出它坏在哪就不要提
- ❌ 规则文件明写"错误一律用 `dict` 传"而你按基本类型偏执提了 blocker ← 铁律一,当场作废
- ❌ 拿基线给既有代码提意见 ← 只看这次 diff 碰过的地方,旧账写进 `notes`
- ✅ 「`repos/order/src/reserve.py:22` 与 `:57` 是同一段库存校验(疑似**重复代码**),
  第二处漏了负数分支——抽成 `ensure_stock()` 两处都调(severity: major)」

## 自检

- [ ] 提的每一条都指得到这次 diff 里的具体位置
- [ ] 每一条都说得出"不改的话下一个人多付什么"
- [ ] 仓库文档认可的写法没有被基线推翻
- [ ] 没有提 linter 已经管的事
- [ ] 措辞是"疑似",不是"违反"
