# spec-fidelity

评审一次改动**是不是需求要的那个东西**时用它。

"做了,但做的不是需求要的"是最贵的失败模式,因为四道闸都放它过去:门禁答"测试绿不绿",
对抗 QA 答"能不能打穿",规范评审答"合不合约定",人工审批那个人手上有整份 diff、
却没有一份逐条对照过的清单。**这份手艺讲的是怎么把那份清单真的做出来。**

## 步骤

1. **先抄标准,再看代码。** 把上下文「计划」段里的验收标准逐条抄进草稿,**连它的 id 一起抄**
   (`a1`、`a2`……)。引用永远用 id,不用"第几条"——序号会随一次重排漂走,而漂走之后
   没有任何东西会报错。凭印象对照时,漏掉的永远是最不显眼、也最容易在实现里被绕过的那条。
2. **每条找出兑现它的那处改动。** 指到文件,能指行就指行。"整体上实现了"不算找到——
   那句话既核对不了也反驳不了。
3. **找不到就是一条 finding**(需求轴的,带上那条标准的 id),而不是一句 note。
   两种"找不到"都算:代码里没有对应的改动;有改动但它满足的是另一件事。
4. **测试也算证据,但只算一半。** 一条断言了该行为的用例是强证据;而"有个测试文件名
   看起来相关"不是。用例断言的东西与验收标准说的不是一回事时,记成 finding。
5. **每条都要填进覆盖表。** 一条标准一行,写清楚证据在哪(字段名与形状见工序契约,
   这里不复述)。表不全的话产物边界会拒收,并告诉你少的是哪条——**那不是格式挑剔**:
   不要求表的话,"没去对照"与"对照过、都满足"在产物上长得一模一样。

## 边界

- **只对照这次的验收标准。** 需求本身写得不好(标准不可判定、互相矛盾)记进 `notes`,
  那是下一次解析要修的事,不是这一轮开发的锅。
- **不要求实现方式。** 验收标准说的是行为;实现绕了远路是**规范轴**的意见,别混进来。

## 反例

- ❌ 「整体符合需求」 ← 核对不了也反驳不了,正是这份手艺要消灭的那句话
- ❌ 「`a2` 应该没问题,代码里看到有相关逻辑」 ← "看到有相关逻辑"不是证据,指到行
- ❌ 把「这里应该抽个函数」算成需求轴 ← 那是规范轴,需求轴只问"做没做需求要的"
- ❌ 用"第 2 条"当锚点 ← 序号会随一次重排漂走;引用用 id
- ❌ 覆盖表里只列了自己找到的那几条 ← 漏掉的那条恰恰是最该被看见的
- ✅ 「`a2`「库存不足时下单失败且不预占」没有对应实现:
  `repos/order/src/reserve.py:41` 在库存不足时仍然写入了预占记录再抛错,
  预占没有回滚(需求轴,severity: blocker)」
- ✅ 「`a1` covered:`repos/order/src/reserve.py:28` 扣减库存,
  `repos/order/tests/test_reserve.py:15` 断言扣减后余量」

## 自检

- [ ] 验收标准逐条抄下来过,引用的是它们的 id 而不是序号
- [ ] 每条都在覆盖表里有一行,没有一条是凭印象填的
- [ ] 每条标为"覆盖了"的都指得到文件(能指行的指了行)
- [ ] 没有把规范轴的意见算成需求轴
- [ ] 需求本身的问题写进了 `notes`,没有算成这一轮的 finding
