# code-critique

对这一轮的开发产出做一次批判性评审。只返回结构化评审结论；运行时统一保存小票。

## 两个轴,分别问一句

- **规范轴(`axis: standards`)**:这份改动有没有违反这个项目自己写下的约定。判据是规则
  文件与约定卡片;项目什么都没写时,判据是 `smell-baseline` 那份手艺里的坏味道基线——
  **但仓库写下的规范永远压过基线**。
- **需求轴(`axis: spec`)**:这份改动是不是需求要的那个东西。判据是上下文里那份计划的
  **验收标准**,逐条对照。

第二个轴是这道工序存在的一半理由:"做了,但做的不是需求要的"过得了门禁、过得了规范评审、
也过得了对抗 QA——**没有人逐条对照的话,它一直要到人工审批那一刻才可能被发现**。

## 怎么走

1. **先把验收标准逐条抄下来。** 上下文里的「计划」段有它们,每条带一个 `id`(`a1`、
   `a2`……)。凭印象对照时,漏掉的永远是最不显眼的那条。
2. **每条验收标准找出兑现它的那处改动。** 找得到就在 `spec_coverage[]` 里记一行
   `covered: true` 并写清楚证据(哪个文件的哪段);找不到就是一条 `axis: spec` 的 finding。
3. **再读约定,读 diff。** 上一轮的产物里有 `changed_files`,顺着它读。
4. **返回符合输出 schema 的 JSON 对象**。不要写代码，也不要自行写产物文件。

## 结构化评审结论要包含什么

- `approved`:这份改动现在就可以送门禁与人工审批吗。true 即结束本环。
- `findings[]`:**最多 20 条,按严重度从高到低排**。每条:
  - `file`(必填,相对 Workspace 根)、`line`(能指就指)
  - `severity`:`blocker` / `major` / `minor`
  - `issue`:问题是什么,一句话说清
  - `suggestion`:**建议怎么改**,要具体到能照着动手
  - `axis`:`standards`(缺省)或 `spec`。**`spec` 的必须带 `acceptance_ref`**——
    它违反的是哪一条验收标准,填那一条的 `id`(如 `"a2"`)。
- `spec_coverage[]`:**要填 `approved: true` 就必须逐条交这张表**,每条验收标准一行
  (`acceptance_ref` + `covered` + `evidence`)。少一条会被产物边界拒收,并告诉你少的是哪条。

## 不要做的事

- 不要重复门禁的工作:测试跑没跑通它已经知道了。
- 不要为了凑数写意见。没有 blocker/major 才能 `approved: true`；minor 可以随意见保留。
- 不要提出与本次改动无关的重构建议——那是另一个任务,写进 `notes` 而不是 findings。
- **不要写"整体符合需求"这类话。** 它既核对不了也反驳不了;覆盖表要的是逐条证据。
