# write-tests

按验收标准写用例。**你不写实现**——写完这一步,用例应该是红的。

## 为什么这件事不能由实现的人顺手做

一个绕过了某条边界的实现,它给自己写的测试大概率绕过同一条边界。**同一个头脑不会用测试
抓自己的盲区**。你在这里的价值全部来自"你还没想过怎么实现":你只能照着验收标准写,而那
正是我们想要的——测试代表验收标准,不是实现的回声。

所以**不要去读实现该怎么写**,也不要在用例里假设内部结构。从外部行为写:给什么、期望什么。

## 红是对的

跑一遍你写的用例,它们应该失败,而且失败信息要说得清"缺的是什么"。

- 全都通过了 → 说明你写的是既有行为的复述,不是这次的验收标准。重写。
- 报的是 import 错误或语法错误 → 那不是"红",那是坏掉的用例。接口名先定下来,让它红在
  断言上,不是红在收集阶段。

## 覆盖什么

**验收标准带「规格」指针时,你的活是把那份规格编码成可执行测试,不是自己重新想一遍要验
什么。** 规格文件已经在你的工作区里(计划那一段列了路径),里面写好了每条用例的
Given / When / Then、覆盖哪个等价类或边界、是正例还是反例。**规格里有的这一轮必须全部落地**
——少一条就是那条标准这次没人验,系统会当场拒并指名是哪一条。

你失去的只是"这次要验什么"的决定权,而那本来就该在需求解析定。**怎么编码仍然全是你的判断**:
用什么夹具、怎么构造 Given 里那个状态、断言写在哪一层、怎么让它红在断言上。规格说的是行为,
不是代码。

没有规格指针的计划(存量任务)照旧:按验收标准自己出题,下面这几条一样适用。

- **每一条验收标准至少一条用例**,一一对应地写,`acceptance_covered[]` 里按验收标准的
  **`id`** 说清楚哪条对哪条(`acceptance_ref: "a1"`)。别拿标准全文当 key:改一个字,
  这份对应关系当场断掉,而没有任何东西会报错。
- **验收标准里的 `seam` 说的是这一条在哪一层验。** 有它就照它写,不要自己另选一层;
  它填的是 `seam_absent_reason` 时,缝由你定,并在 `notes` 里说明你选了哪一层。
- 边界值与异常路径:空、零、负数、超长、重复调用。这些恰恰是实现最容易绕过去的地方。
- 不要为了覆盖率写用例。一条断言不了任何行为的用例比没有更糟——它会让门禁变绿。

## 不要做的事

- 不要碰实现代码。你的写集只有测试路径,碰了会被判越权并回滚整轮。
- 不要把用例写成"必过"。你出的是题,不是答案。

## result.json 要写什么

- `test_files[]`:你写了哪些文件。
- `acceptance_covered[]`:每条验收标准(按 `id`)对应哪几条用例。
- `red`:跑了之后是不是真的红。**这一条不许猜**,跑一遍再填。
- `passed`:你有没有把题出出来(不是"用例有没有通过")。
